PROJECT 01 · 팀장

LawSight — AI 판례 분석 및 소송 전략 시스템

변호사가 자연어로 사건을 입력하면 유사 판례를 찾고, IRAC 형식의 소송 전략 리포트를 생성하는 AI 리서치 보조 서비스

구분
2026 한이음 드림업 (과기정통부) · Team 404 · 4인 · 2026.04 ~ 10
본인 역할
팀장(PM) 겸 Data · DB · 배포 인프라 총괄
기술 스택
PostgreSQL · ChromaDB · KoSBERT · BM25+RRF · FastAPI · GPT-4o · AWS EC2
서비스
www.lawsight.co.kr ↗

상황판례 리서치는 수작업, 원천 데이터는 비정형

  • 변호사의 판례 검색·비교는 사건마다 수작업
    현직 변호사 인터뷰 결과 “사실관계가 비슷한 판례”와 “근거 없는 답변(환각) 배제”가 핵심 니즈
  • 원천은 국가법령정보 공공 API — 목록과 본문이 분리
    판결문은 장문의 비정형 텍스트
  • 표기 불일치·중복이 섞인 원시 데이터
    같은 법원이 여러 이름으로 기록(원시 104종), 동일 판례 중복 수집 발생
  • 제한된 자원과 일정
    4인 · 7개월, 클라우드 지원금 범위의 EC2 단일 인스턴스에서 운영

해결 과제데이터가 검색 품질을 결정한다

  1. 대규모 판례 수집 자동화2단계 API 호출로 수만 건을 중단 없이, 재실행 가능한 구조로 수집
  2. 비정형 판결문 정제·표준화파싱 · 법원명 표준화 · 중복 제거 · 테이블 간 정합성 보장
  3. 정형 + 벡터 저장소 설계메타·본문은 PostgreSQL, 의미 검색은 ChromaDB로 역할 분리
  4. 제한 자원에서 실서비스 운영검색 응답 속도·메모리 안정성 확보, HTTPS 배포

액션 ③ 운영 장애 대응

문제 → 원인 → 조치 → 효과를 측정 가능한 지표로 정리했습니다.

Case 1요청마다 BM25 인덱스 재로딩 — 병목 원인 분석·개선

문제
검색 요청마다 383MB 인덱스를 디스크에서 재로딩 → 20~60초 타임아웃
원인
인덱스 로딩이 요청 처리 경로 안에 있어 매 요청이 I/O + 역직렬화 비용을 전부 부담
조치
검색 서비스를 모듈 레벨 인스턴스로 전환, 서버 시작 시 1회만 로딩

20~60초 → 0.68초 · 실패율 0%

Case 2메모리 부족(OOM) — 제한 자원 환경에서의 팀 공동 대응

문제
RAM 4GB에서 인덱스·모델·벡터DB 동시 상주 → OOM killer가 백엔드 종료
원인
journalctl 추적 — 인스턴스 증설 후에도 재발해 단순 사양 문제가 아님을 확인, 메모리 상주 객체와 검색 범위를 함께 점검
조치
t3.medium 증설 · swap 4GB 구성 (팀: BM25 인덱싱 범위 축소)

swap 3.2GB → 687MB

Case 3ChromaDB 대량 적재 세그폴트 — 분할 적재 및 재구축

문제
72만 청크를 단일 컬렉션에 적재하는 중 세그폴트 반복
원인
DB 무결성은 정상, Python 3.11 / 3.14 모두에서 재현 → 단일 컬렉션 규모·메모리 한계를 우선 원인으로 판단
조치
2개 컬렉션(571,603 / 152,326)으로 분할 적재, Python 3.11 소스 빌드 + 전용 venv, 체크포인트로 중단 지점부터 재개

723,929 청크 적재 완료

  3. 개인화 RAG사용자 이력을 임베딩해 유사 이력 top-3를 응답에 반영
  4. 운영 DB 신뢰성클라우드 운영 DB와 설계 문서 일치, 권한 우회 취약점 차단
